# Voyz Cloud: GitHub Pages + Supabase

Облачный слой использует Supabase и GitHub Pages. Проект Supabase `mjlpcvqrwbtmabivgxuj` создан в организации Voyz; миграция `voyz_cloud_v1` применена. Локальный режим приложения работает отдельно от этого слоя. Статус публикации и входа в приложение указан в основном README проекта.

## Подключение

1. Создайте отдельный проект Supabase. В SQL Editor выполните `001_voyz_cloud.sql` один раз от роли `postgres`. Включите `pgcrypto` в схеме `extensions`, если проверка миграции сообщает об отсутствии функции.
2. В Data API оставьте `public` среди exposed schemas. **Не добавляйте `voyz_private`**. В таблице `voyz_tours` включён RLS; прямые изменения из браузера запрещены.
3. Включите Email Auth. При использовании своего SMTP в шаблонах писем **Magic Link / OTP** и **Confirm signup** добавьте `{{ .Token }}`: пользователь вводит присланный код в приложении. Не ограничивайте длину кода ровно шестью цифрами: она задаётся настройками Auth. С 3 июня 2026 новые проекты Free со встроенным SMTP не позволяют менять шаблоны: стандартное письмо содержит ссылку. Для таких проектов приложение должно поддерживать вход по ссылке либо нужно подключить свой SMTP.
4. Для реального использования подключите свой SMTP. Встроенная почта Supabase ограничена и не подходит для обычной командной работы. Задайте точный Site URL и разрешённые Redirect URLs для адреса GitHub Pages, включая путь репозитория.
5. Укажите в конфигурации браузерного приложения URL проекта `https://<project>.supabase.co` и **publishable key** `sb_publishable_…`. Это публичная конфигурация. `sb_secret_…`, service-role key, пароль БД и токены управления никогда не должны попадать в `dist/`, GitHub или браузер.
6. Опубликуйте только содержимое `dist/` через GitHub Pages. Пример workflow находится в `pages-workflow.example.yml`; скопируйте его в `.github/workflows/pages.yml` репозитория с `dist/` в корне и выберите Settings → Pages → GitHub Actions. Бэкапы CRM, тестовые данные, журналы и папка `cloud/` в публичный артефакт не входят.
7. После изменений схемы повторяйте `verify.sql` от роли `postgres`. Проверки создают два случайных тестовых аккаунта внутри транзакции и заканчиваются `ROLLBACK`, не оставляя тестовых аккаунтов и маршрутов. Они уже выполнены в созданном проекте Voyz без ошибок 3 октября 2026.

## RPC-контракт

Все вызовы: `POST <SUPABASE_URL>/rest/v1/rpc/<name>`, JSON body, `Content-Type: application/json`, `apikey: <publishable key>`. Для владельца дополнительно `Authorization: Bearer <user access_token>`. Для анонимного просмотра ссылки достаточно `apikey`; publishable key не является JWT и не передаётся как Bearer.

| RPC | JSON-параметры | Результат |
| --- | --- | --- |
| `voyz_list_tours` | `{}` | Массив метаданных всех своих туров, включая удалённые tombstones |
| `voyz_get_tour` | `{p_tour_id}` | `{id,revision,updatedAt,deletedAt,document}` либо `null` |
| `voyz_put_tour` | `{p_tour_id,p_expected,p_document}` | `{id,revision,updatedAt,deletedAt}` |
| `voyz_delete_tour` | `{p_tour_id,p_expected}` | Та же метаинформация, `deletedAt` заполнен |
| `voyz_restore_tour` | `{p_tour_id,p_expected}` | Та же метаинформация, `deletedAt:null` |
| `voyz_create_share` | `{p_tour_id,p_expires_at:null}` либо дата ISO | `{id,token,expiresAt}`; токен возвращается один раз |
| `voyz_list_shares` | `{p_tour_id}` | Массив `{id,tourId,createdAt,expiresAt,revokedAt}` без токенов |
| `voyz_revoke_share` | `{p_share_id}` | `{id,revokedAt}` |
| `voyz_read_share` | `{p_token}` | `{document,revision,updatedAt,expiresAt,readOnly:true}` либо `null`; работает без входа |

`voyz_list_tours` возвращает `{id,revision,title,startDate,endDate,dayCount,createdAt,updatedAt,deletedAt}`. Порядок — дата создания, затем ID. `voyz_get_tour` позволяет владельцу прочитать сохранённый документ удалённого тура для восстановления. Отсутствующая или чужая запись возвращает `null`. Все owner IDs выводятся из `auth.uid()`; клиент не передаёт владельца.

`p_expected:0` создаёт новый тур только при отсутствии записи с таким ID у текущего владельца. Для изменения нужна последняя подтверждённая сервером ревизия. Ревизия атомарно увеличивается на 1. Повторная отправка старой версии, попытка сохранить поверх tombstone, устаревшее удаление и восстановление возвращают `REVISION_CONFLICT` (`code:P0001`), а не перезаписывают данные.

Другие ошибки: `AUTH_REQUIRED`, `INVALID_REVISION`, `INVALID_DOCUMENT`, `INVALID_EXPIRY`, `TOUR_NOT_FOUND`, `SHARE_NOT_FOUND`. Проверяйте `message`, `code` и HTTP-статус; не считайте сетевую ошибку подтверждением изменения. После ответа, потерянного в сети, сначала перечитайте соответствующий тур: операция могла успеть выполниться.

Документ тура остаётся версии 2: `{kind:'voyz-tour',version:2,id,tour,days,connections,view,crm}`. Сохраняются ширина карточек, `lodgingName` / `lodgingUrl`, CRM-поля `gender` / `departureCity`. Фото пока встроены как data URL. Лимит одного документа — 32 MiB, 100 дней и 100 событий на день; это транспортные ограничения, не обещание бесконечной вместимости БД.

## Синхронизация без потери версий

- Сначала сохраняйте изменения локально. Храните очередь и `{remoteRevision,baseDocument}` отдельно от маршрутного JSON, с ключами **Supabase project + Auth user ID + tour ID**.
- При первом подключении существующей локальной библиотеки получите список удалённых туров. Сохраните локальный бэкап и добавьте локальные туры в облако **как копии с новыми ID**, затем объедините их с удалёнными. Не сопоставляйте туры по названию и не удаляйте удалённые записи, которых нет на текущем устройстве.
- Сохраняйте по одному изменённому туру. Сериализуйте операции для одного ID; `p_expected` берётся только из последнего подтверждённого ответа. Глобальная библиотека не загружается на каждое нажатие клавиши.
- При конфликте сохраняйте обе версии: локальная копия остаётся в очереди, удалённая читается отдельным документом. Предложите сохранить локальную версию новым туром либо принять удалённую после бэкапа. Нельзя просто обновить `p_expected` и повторить старый payload.
- Tombstone тоже является новой ревизией. Если локальных изменений нет, примените удаление. Если они есть — остановите синхронизацию этого тура и предложите сохранить новую копию. Обычное сохранение не может воскресить удалённый тур.
- При выходе остановите очередь и смените пространство локального кеша. Нельзя показывать CRM предыдущего аккаунта или загружать его от другого пользователя.

## Ссылки для гидов

Используйте URL вида `<SITE_URL>#share=<64 hex characters>`. Фрагмент не отправляется серверу GitHub Pages. В RPC передавайте токен в POST body. В БД хранится SHA-256 токена, а не исходная ссылка.

Ссылка показывает **актуальную синхронизированную версию** конкретного тура. После перезагрузки гид увидит обновления. Сервер собирает явный allowlist полей маршрута, дней, таймингов и стрелок. CRM, клиенты, оплаты и неизвестные дополнительные поля не возвращаются, даже если они есть в документе. Просмотр не имеет права редактирования. Ссылку можно отозвать или ограничить по времени. Удаление тура отзывает все его ссылки; восстановление их не включает заново.

Названия/содержимое заметок и ссылки на проживание входят в маршрут. Если вручную написать личные данные клиента в обычной заметке, она тоже будет доступна получателям ссылки. Отзыв закрывает следующие запросы, но не удаляет уже скачанные фото/PDF или офлайн-копии с чужих устройств.

## Что проверено и что ещё требуется

3 октября 2026 `verify.sql` успешно выполнен через Supabase в проекте `mjlpcvqrwbtmabivgxuj` на PostgreSQL 17.11. Проверены сохранение документа без потерь, увеличение ревизии, отклонение устаревшего сохранения/удаления, изоляция двух владельцев с одинаковым ID тура, RLS прямого чтения, запрет анонимного чтения и прямых записей, актуальность ссылки, исключение CRM и неизвестных приватных полей, сохранение проживания и ширины, отзыв/истечение ссылки, мягкое удаление и восстановление. После `ROLLBACK` количество туров, ссылок и тестовых аккаунтов осталось нулевым; реальные данные не изменялись.

Проверены права всех 17 функций: у каждой закреплён пустой `search_path`; публичные функции используют `SECURITY INVOKER`, привилегированные функции находятся в `voyz_private`. `anon` может вызывать только RPC чтения конкретной ссылки. У `authenticated` нет прямого изменения таблиц. Security Advisor не сообщил предупреждений или ошибок; единственный INFO — RLS без политик на закрытой `voyz_private.shares` — соответствует намеренному запрету прямого доступа ([описание проверки](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)). Performance Advisor не сообщил замечаний. Подробная запись проверки хранится локально в `qa-output/cloud-live-verification.json` и не входит в публичный сайт.

SQL-проверка подтверждает поведение БД и ролей; она не подтверждает доставку реального письма, вход пользователя или синхронизацию двух браузеров через интернет. Эти сценарии проверяются отдельно при публикации; основной README содержит их актуальный статус.

Кеш в браузере принадлежит конкретному адресу и устройству. Данные localhost не появятся автоматически на github.io: их нужно импортировать/отправить в облако. Сервис-воркер может хранить интерфейс; маршруты и фото должны отдельно сохраняться в IndexedDB для офлайна. Неуспешная загрузка в облако не должна стирать локальные данные.

Supabase Free может приостанавливать неактивные проекты. Для поездок сохраняйте актуальные маршруты офлайн и делайте JSON-бэкапы. Масштаб зависит от тарифа и фотографий. Большие библиотеки со временем лучше вынести в private Storage с подписанными URL; публичный bucket делает изображения доступными любому обладателю URL.
